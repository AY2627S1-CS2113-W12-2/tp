Design

Overall architecture

TutorLedger is a single-process command-line application. A shared in-memory store holds the tutor's records, feature handlers interpret commands, and persistence saves the records in a local text file. The diagram groups the existing classes by responsibility; these boxes are not separate services or separate Java packages. All application classes belong to seedu.tutorledger.

Architecture overview. Arrows indicate dependencies and use, rather than chronological execution.

Responsibility Main classes Role
Application entry point TutorLedger Creates the shared store and handlers, reads console input, routes commands and coordinates automatic saving.
Feature commands StudentCommands, LessonCommands, PaymentCommands, HomeworkCommands, ScoreCommands, TaskCommands, TopicCommands, LessonFilterCommand Validate feature-specific input, read or update records, and return display text.
Shared helpers ArgumentParser, CommandAliases, HelpCommand Parse prefixed fields, expand command shortcuts, and provide help text.
Data and models TutorLedgerData, Student, Lesson, Homework, Score, FollowUpTask Own record collections and permanent ID counters; validate values and represent records as immutable objects.
Persistence StorageCommands, Storage Load and reload the shared store, compare snapshots, and encode or decode data/tutorledger.txt.

At startup, TutorLedger creates one TutorLedgerData and passes it to the handlers and persistence coordinator. StorageCommands.loadOnStartup() restores that store before the input loop starts. Each line is expanded through CommandAliases; handles checks route it to the appropriate handler. Unclaimed input reaches StudentCommands, which also handles help and unknown commands.

Before an ordinary feature command, the entry point records a storage snapshot. After the handler returns, it calls saveIfChanged; persistence writes only when the records changed. Explicit save and reload commands use the persistence path directly. Feature handlers do not save files themselves, and the data model does not depend on persistence.

Sharing a store makes edits immediately visible to other commands without duplicating records. Keeping file operations in persistence allows commands to operate on in-memory data during tests. This design does not require a common command interface: the current handlers use static handles methods and instance execute methods. The more detailed class, sequence and activity diagrams below explain the selected implementation decisions.

Implementation

Storage

The storage feature keeps every record in one plain-text file, data/tutorledger.txt, so that data survives restarts and a tutor can fix or bulk-edit records in a text editor.

Storage responsibilities. The entry point coordinates persistence; StorageCommands shares the live store and delegates encoding and file I/O to Storage.

  • Storage knows the file format and does the file input/output. It never prints anything, so it can be tested on its own.
  • StorageCommands runs save and reload, loads the file at startup and saves automatically. It turns file errors into messages for the user, following the same handles/execute pattern as the other command classes.
  • TutorLedgerData gained importLesson, importHomework, setNextLessonNumber, setNextHomeworkNumber and replaceAllWith so that records can be restored with their saved IDs.

File format

Each record is one line of fields separated by a vertical bar, |, with a space on each side:

NEXT | S3 | L2 | H2 | A2 | T2
S | S1 | Amirah Binte Rahman | Sec 3 | 91234567 | E Math | A Math
L | L1 | S1 | 15-09-2026 | 1600 | A Math | 60 | present | paid | Quadratics \| discriminant |  | 60 | 60
H | H1 | S1 | 29-09-2026 | outstanding | Worksheet 4A
A | A1 | S1 | 07-09-2026 | 28 | 40 | WA1
T | T1 | pending | 16-10-2026 | S1 | Bring Worksheet 4B
  • The NEXT line saves the ID counters. Without it, deleting the newest student and restarting would hand the deleted student's ID to the next new student, breaking the rule that IDs are never reused.
  • A | or \ inside a value is escaped as \| or \\, so notes and subjects can contain any text.
  • Values are written in the same format the user types them (e.g. DD-MM-YYYY), so a hand-edited file uses the rules users already know.

Alternatives considered: JSON (via a library such as Jackson) handles nesting and escaping for us, but it is harder for a tutor to edit by hand, and it needs a third-party library. CSV is similar to the chosen format, but its quoting rules are less obvious to people editing it by hand.

Loading and validation

Storage.decode first reads students and the NEXT line, then processes rates, archive markers, lessons, homework, scores and follow-up tasks. This permits linked records to appear before their student line. Student-linked records must resolve to a valid student; follow-up tasks may also be unlinked. Imports reuse model validation and reject malformed values, duplicate IDs and occupied lesson slots. Command-specific restrictions, such as requiring restoration before scheduling for an archived student, are separate from loading historical records.

Current lesson rows have thirteen fields, ending with NOTES | CANCELLATION_REASON | MINUTES | AMOUNT_PAID. The loader also accepts older lesson layouts. Fees are loaded as saved and are not recomputed from current rates. Rate and archive metadata use separate R and ARCHIVED lines so legacy subject fields remain unambiguous.

A line that fails a check is skipped and reported as Line N: reason. Loading carries on with the remaining lines, so one typo does not lose the whole file.

Automatic saving

Before each command, the main loop takes a snapshot() (the text the file would contain). After the command, saveIfChanged compares a new snapshot with it and writes the file only if they differ.

Automatic saving. StudentCommands is one representative feature handler. A changed snapshot triggers a save; unchanged records leave the file untouched.

  • Comparing snapshots means a command that teammates add later is saved automatically. Nobody has to remember to update a list of "commands that change data".
  • Commands that only display data never write the file, so they cannot overwrite a tutor's hand edits before reload.
  • save and reload skip the automatic save. In particular, reload must not save, or the lines it just skipped would be erased before the tutor could fix them.
  • The trade-off is encoding the data twice per ordinary command. The work grows with the stored records; this guide does not assume a measured response-time guarantee.

Alternative considered: saving after every command, whether or not it changed anything, is simpler. But a read-only command such as list would then overwrite hand edits made while the app is open.

Possible improvement: write to a temporary file and then rename it over the data file. A temporary-file replacement can reduce the risk of a partial write; an implementation would also need to handle filesystem and rename failures.

Income summaries

PaymentCommands handles income MM-YYYY and income YYYY. Monthly summaries select non-cancelled lessons with a positive amountPaid, group them by lesson date, and sum Lesson.getAmountPaid(). Yearly summaries apply the same rule to each of the twelve months, including months with a zero total. Partial payments contribute the amount actually received; an unpaid lesson contributes nothing. A free lesson is settled but contributes no income. The reporting period uses the lesson date, not a separate payment timestamp, because no transaction-date ledger is stored.

The output is calculated from the current lesson collection without changing any records. Cancelled lessons remain in the history but are excluded from income. Editing a fee preserves the amount already received; the fee-edit rules below prevent an edit from manufacturing or discarding a payment.

Scores and progress

These features let a tutor record test results and review a student at the end of a term.

  • Score is an immutable record of one test result, like Lesson and Homework. Its constructor checks every value, for example that the marks are not more than the total. A score therefore cannot exist in an invalid state, whether it was typed in or loaded from a hand-edited file.
  • ScoreCommands follows the same handles/execute pattern as the other command classes. The main loop routes score, scores and progress to it.
  • TutorLedgerData stores scores in a map keyed by ID, with a counter that never decreases, as it does for lessons and homework. deleteStudent also removes the student's scores, and Deletion reports how many were removed.
  • Storage saves each score as an A line. The score counter is a fifth, optional field on the NEXT line, so data files written before this feature still load.

Recording a score

The sequence diagram below shows score S1 WA2 m/33/40.

  1. The test name is everything before the first m/ or d/, so it can contain spaces, like an assign description. The rest goes to the shared ArgumentParser, so m/ and d/ can be typed in any order.
  2. TutorLedgerData.addScore looks up the student first, so a score can never belong to a missing student. It then creates the Score, which validates the values, and stores it under the next ID.
  3. ScoreCommands sorts the student's scores by date and compares the new score with the one before it. The tutor sees at once whether the student did better or worse.

Any invalid value throws IllegalArgumentException before anything is stored. execute turns this into an Error: ... message and logs it at WARNING level.

Design decisions

  • Marks are BigDecimal, not double. Half marks such as 17.5 are common, and double cannot store some decimals exactly. The data file would then show values like 17.499999. Lesson fees use BigDecimal for the same reason.
  • Scores are compared as percentages. Tests have different totals (40 marks for a class test, 100 for an exam), so raw marks cannot be compared. Percentages are rounded to 1 decimal place with HALF_UP.
  • The date defaults to today. Tutors usually record a score on the day the script is returned. Alternative considered: making d/ compulsory is stricter, but it adds typing for the most common case.

Summarising progress

progress STUDENT_ID [from/DATE] [to/DATE] gathers the student's lessons and scores in the period and summarises them. The activity diagram shows how each lesson is counted.

  • Cancelled lessons are excluded before attendance is counted.
  • Lessons after today are skipped because they cannot have attendance yet. Counting them as "not recorded" would wrongly suggest the tutor forgot to record them.
  • Unrecorded past lessons are reported, but they are left out of the rate. Otherwise a tutor who has not yet recorded yesterday's lesson would see a lower rate than the student deserves.
  • A late arrival counts as attending. The tutor still taught the lesson, and the separate late count keeps lateness visible.
  • Without from/, the period starts at LocalDate.MIN, so all of the student's records are included.

scores and progress share the private helpers scoreTable and trend, so the score list looks the same in both commands.

Alternative considered: storing term dates, so a tutor could type progress S1 term/3. Schools' term dates differ, and a tutor would have to set them up first. from/ and to/ work for any period with no setup.

Possible improvements: let edit and delete accept a SCORE_ID, so a mistyped score can be fixed without editing the data file. Also show the average score by subject, once scores record a subject.

Follow-up tasks

Between lessons, a tutor collects small jobs: bring a worksheet, return a marked script, print a calendar. Follow-up tasks keep these reminders in TutorLedger, next to the lessons they belong to:

Command Purpose
task [STUDENT_ID] DESCRIPTION [d/DUE_DATE] Log a reminder, optionally for one student and by a date
tasks [STUDENT_ID] List pending reminders, soonest due first, with overdue ones marked
done TASK_ID Tick a reminder off

next also lists the student's pending reminders, so they are seen at the moment the tutor prepares for the lesson.

Responsibilities and object relationships

  • FollowUpTask is an immutable record, like Homework. Its student and due date are optional, because some reminders (such as "Print term calendar") are not about one student or day. The getters return Optional, so callers cannot forget to handle a task that has neither.
  • TaskCommands follows the same handles/execute pattern as the other command classes. The main loop routes task, tasks and done to it.
  • TutorLedgerData stores tasks in a map keyed by ID, with a counter that never decreases, as for every other record. A task links to a student by ID rather than holding the Student object. Student profiles are replaced whenever they are edited, so a stored object would go stale, but an ID always stays valid.
  • LessonCommands.describeFollowUps adds a Follow-ups: line to next. It reuses TaskCommands.DISPLAY_ORDER, so reminders are sorted the same way in both commands.

Logging a task

The sequence diagram below shows task S1 Bring Worksheet 4B d/16-10-2026.

  1. A regular expression splits off a final d/DUE_DATE. As with assign, the date must come last, so the description may contain spaces and commas.
  2. If the first remaining word looks like a student ID (S1), the task is linked to that student and the rest is the description. Otherwise the whole text is the description.
  3. TutorLedgerData.addTask looks the student up first. A task can therefore never point to a missing student. It then creates the task with the next T ID.

done TASK_ID works the same way as submit for homework. FollowUpTask.asDone() returns a copy with the new status, and replaceTask stores it under the same ID.

Design considerations

  • Student ID as an optional first word, rather than a prefix such as for/S1. Most other commands put the student ID first (assign S1 ..., score S1 ...), so the tutor does not need to learn another prefix. A description that happens to start with a word like S1 would be read as a student ID. This is unlikely, and the confirmation line (for S1 ...) makes it obvious.
  • Mark done, rather than delete. A done task stays in the data file, so the tutor can still see in the file what was done. tasks and next simply leave done tasks out. Alternative considered: deleting the task on done keeps the file smaller, but loses the record.
  • Show reminders in next. The story's goal is to avoid forgetting things "between lessons". A separate list is easy to forget to check, but next is already what the tutor runs before a lesson. The line only appears when there are pending reminders, so the usual next output is unchanged.
  • Deleting a student deletes their tasks. A reminder about a student who is no longer taught is not useful. Tasks not linked to anyone are kept. Because the tasks are removed too, a student with follow-up tasks gets the deletion warning (see Student deletion warnings), so reminders are never lost silently.

Defensive checks and persistence

  • Invalid input (an unknown student, an impossible date, a blank description, a repeated done) throws IllegalArgumentException before anything is stored. execute turns it into an Error: ... message and logs it at WARNING level.
  • Assertions check things that only a coding mistake could break: a new task is pending, the counter advanced, done really stored a done copy, and tasks lists no done tasks.
  • Storage saves each task as a T line with six fields. A missing due date or student is an empty field. The task counter is an optional sixth field on the NEXT line, so data files saved before this feature still load.
  • TaskCommandsTest and StorageTest cover each command, the next integration, cascade deletion, and loading old and hand-edited files.

Possible improvements: let edit change a task's description or date, and accept a time (e.g. d/16-10-2026 t/1500) for reminders that must be done before a particular lesson.

Lesson scheduling and records

A tutor's week revolves around lessons, so these commands let them plan lessons, record what happened, and change plans when real life gets in the way:

Command Purpose
schedule STUDENT_ID d/DATE t/TIME s/SUBJECT [f/FEE] [dur/MINUTES] [w/WEEKS] Plan one lesson, or the same slot for 2–52 weeks
log STUDENT_ID d/DATE t/TIME s/SUBJECT f/FEE a/ATTENDANCE [note/NOTES] Add a lesson that already took place, with its outcome
lessons [week] List today's or this week's lessons, earliest first
next [STUDENT_ID] Summarise the next lesson and what to prepare for it
record LESSON_ID a/ATTENDANCE [note/NOTES] Record attendance and notes for a lesson that has taken place
edit LESSON_ID ... / delete LESSON_ID Correct any detail of a lesson, or remove one entered by mistake
reschedule LESSON_ID [d/DATE] [t/TIME] Move a lesson that has not taken place yet
cancel LESSON_ID r/REASON Call off a lesson but keep it, with the reason, in the history

Responsibilities and object relationships

LessonCommands parses and runs every lesson command. Like the other command classes, it follows the handles/execute pattern: the main loop asks LessonCommands.handles(line) whether the line is a lesson command, then passes the line to execute, which returns the text to display. edit and delete are also student commands, so handles claims them only when the ID after the command word starts with L. For example, edit L3 t/1700 is routed here, while edit S1 p/91234567 is left for StudentCommands.

Figure 1. LessonCommands changes lessons only through TutorLedgerData, which owns every Lesson.

  • TutorLedgerData is the only class that stores lessons. It gives each new lesson the next ID (L1, L2, ...) and checks that no two lessons start at the same date and time (ensureSlotFree). It never reuses an ID, even after a lesson is deleted, so an ID in an old note or message never points at a different lesson.
  • Lesson is immutable: a change produces a new copy through withDetails or withCancellation, and TutorLedgerData.replaceLesson swaps the copy in. Attendance is a separate enumeration, so a cancelled lesson (cancellationReason is set) is never confused with one the student missed (ABSENT).
  • ArgumentParser splits prefixed values such as d/01-12-2026 s/A Math. It was extracted from StudentCommands so that every command reads a prefix the same way. The values may be in any order, values may contain spaces, and a repeated or unknown prefix is rejected.

Fees and durations are omitted from Figure 1; see Default hourly rates for how a lesson's fee is chosen.

Scheduling a weekly slot

Most students have one regular weekly slot, so schedule ... w/WEEKS adds that many lessons in one command. Figure 2 shows schedule S1 d/01-12-2026 t/1600 s/A Math f/60 w/3. Every lesson command begins by splitting its arguments in the same way, so that step is drawn once, in Figure 3, and referred to with a ref frame.

Figure 2. Every week is checked before any lesson is stored.

Figure 3. The parse ID and fields fragment used by Figures 2 and 5.

  1. LessonCommands looks up the student and checks that they take the subject. It uses the student's own spelling of the subject, so a math and A Math are not stored as two subjects.
  2. TutorLedgerData.addWeeklyLessons builds one Lesson per week, numbering them from the next lesson ID, and checks each slot as it goes.
  3. Only after every slot passes does it store the lessons. If week 3 clashes with an existing lesson, the tutor sees Error: <ID> already starts at that date and time. and no lesson is added. The counter only moves when lessons are stored, so a rejected command never skips an ID.

Changing a lesson: record, edit, reschedule and cancel

These four commands share one pattern: get the lesson, make a changed copy, check it, then call replaceLesson. Figure 5 shows reschedule L3 d/16-12-2026.

Figure 5. The original lesson stays in the store until its validated replacement is stored.

  • replaceLesson checks the slot only when the date or time has changed, so recording attendance on a busy day is never blocked by a clash check.
  • If any check fails, nothing has been replaced, so a rejected command never leaves a half-changed lesson. The store replaces its reference only after validation. The handler may still read the original object when displaying the old slot; map replacement does not explicitly destroy a Java object.
  • edit and reschedule both change the slot, but they serve different purposes. edit corrects a record, so it can change any lesson, including a past one. reschedule describes a real-life change of plan, so it rejects a lesson that has already taken place (it has attendance or notes), a cancelled lesson, an unchanged slot, and a time that has already passed.
  • record and log only accept lessons dated today or earlier, because a lesson that has not happened has no attendance yet. edit enforces the same rule when it sets attendance or notes.
  • cancel keeps the lesson with its reason. A cancelled lesson frees its slot, is left out of owed and unpaid, and still appears in lessons marked (cancelled: REASON). Any positive amount received, including a partial payment, triggers a reminder to refund or carry over that amount. No refund is recorded automatically.

Preparing for the next lesson

next [STUDENT_ID] gathers everything a tutor checks just before a lesson. Figure 6 shows how the lesson is chosen and summarised.

Figure 6. Only lessons that can still take place are considered.

The summary is built from existing records each time; nothing extra is stored. "Unpaid" totals the remaining balances of non-cancelled lessons up to today, including partially paid lessons, using the same balance rule as owed. Pending follow-up tasks for the selected student appear when there are any.

Design considerations

Aspect: How a lesson is changed

  • Alternative 1 (current choice): Lesson is immutable; each change creates a copy that TutorLedgerData.replaceLesson swaps in.
    • Pros: a failed check leaves the stored lesson untouched. Every change goes through one method, so the slot check cannot be skipped by accident.
    • Cons: each change creates a new object, and copy methods must carry over every field (assertions in withDetails check this).
  • Alternative 2: give Lesson setters and change it in place.
    • Pros: simpler to write, and no copying.
    • Cons: a command that fails half-way leaves a half-changed lesson. Any code holding the lesson could move it into an occupied slot without the store noticing.

Aspect: How a weekly slot is stored

  • Alternative 1 (current choice): expand w/WEEKS into separate lessons when scheduling.
    • Pros: each week can be recorded, rescheduled, cancelled or paid for on its own. The storage format and every other command work unchanged.
    • Cons: a slot is limited to 52 weeks, and changing the time of the whole slot means changing each lesson.
  • Alternative 2: store a recurring rule and generate lessons when they are needed.
    • Pros: no end date, and one change moves every future week.
    • Cons: every exception (one week moved or cancelled) must be stored against the rule. Every command that reads lessons, including payments and storage, would need to understand rules.

Aspect: How a called-off lesson is handled

  • Alternative 1 (current choice): cancel keeps the lesson with a reason.
    • Pros: the history shows why a lesson did not happen, which matters when a parent asks about a payment.
    • Cons: commands that list, count or charge lessons must remember to skip cancelled ones.
  • Alternative 2: delete the lesson.
    • Pros: no special cases elsewhere.
    • Cons: the record of a lesson that was planned (and perhaps paid for) disappears. delete remains available for lessons entered by mistake.

Defensive checks and testing

User mistakes, such as a bad date or a clashing slot, throw IllegalArgumentException. execute turns this into an Error: ... message, so the program never crashes on bad input and the checks work whether or not assertions are enabled. Assertions check things only a bug could break, for example that a recorded copy really has attendance and that the lesson counter advanced after storing. Each command logs what it did at FINE level, so the trace is available for debugging without appearing on the tutor's screen.

LessonCommandsTest covers each command's normal use and its rejections, and uses a fixed Clock so tests about "today" and "the past" do not depend on the real date. TutorLedgerDataTest covers ID allocation, slot conflicts and the all-or-nothing weekly scheduling.

Default hourly rates

An independent tutor often charges the same student the same hourly rate for many lessons. Requiring f/60 every time repeats information and makes it easy to enter an inconsistent fee. This enhancement lets the tutor store that rate on the student and schedule a lesson using its duration. For example, after edit S1 r/60, schedule S1 d/20-10-2026 t/1600 s/E Math dur/90 creates a lesson costing $90.00. Omitting dur/ means 60 minutes. An explicit f/25 instead charges $25 for the whole lesson.

Responsibilities and object relationships

The feature extends the existing command, model and storage components. StudentCommands parses r/ on add and edit; LessonCommands parses optional dur/ and f/ on schedule. Both use ArgumentParser, so prefixes keep their existing case-insensitive, order-independent behaviour. TutorLedgerData chooses the total fee when creating a lesson. This puts the business rule at the shared data boundary rather than only in a particular command handler.

Figure 1. The store owns student and lesson records; a lesson identifies its student by permanent ID.

Student stores an optional BigDecimal rate. Its getter returns Optional<BigDecimal> so callers must distinguish an unset rate from a valid rate of zero. A missing rate means that scheduling needs an explicit fee; zero means that the lesson is free. Existing constructors still create students without a rate. Existing withDetails operations preserve the rate, including subject changes.

Lesson stores both durationMinutes and its total fee. These are immutable values. Existing lesson constructors default to 60 minutes, while the new overload accepts a validated duration. Copies created for attendance, notes, payment status and other edits retain the duration unless it is explicitly edited. This preserves existing callers without requiring changes to unrelated feature handlers.

Setting and clearing a rate

add ... r/60 creates the entire profile, including subjects and rate, before the data store inserts anything. Invalid rates therefore cannot leave a partially created student or consume an ID. edit S1 r/65 creates a replacement profile, validates it, then replaces the existing map entry. The original profile remains available until all validation succeeds.

Figure 2. A rate edit replaces a validated student and uses the existing automatic-save path.

Omitting r/ during an edit preserves the current rate. A bare edit S1 r/ deliberately clears it, matching the existing convention for clearing subjects with s/. A bare r/ on add is rejected: there is no existing rate to clear, so omission already expresses that intent. Repeated r/ prefixes are rejected rather than choosing a value silently. view S1 reports either the dollar rate per hour or Default hourly rate: not set.

Scheduling and keeping charges stable

The new addLesson overload accepts duration and an optional explicit fee. An explicit fee has priority and represents the entire lesson charge, regardless of duration. Otherwise, the method obtains the student's default rate. If neither source is available, it returns an error explaining both remedies: set the student's rate or supply f/FEE.

Single and weekly scheduling share resolveLessonFee, so schedule ... dur/90 w/3 gives each of the three lessons the same fixed duration-based fee. Weekly scheduling still validates every slot before inserting any lessons. A conflict in a later week therefore leaves records and ID counters unchanged.

Figure 3. Calculation happens before insertion; the result is stored as the lesson's fixed charge.

The calculation is hourly rate × duration in minutes ÷ 60. All money uses BigDecimal; conversion to double would introduce binary floating-point approximation. Division rounds once to two decimal places using HALF_UP. For example, $60.01/hour for 30 minutes produces $30.005 before rounding and $30.01 afterwards. Multiplication is performed before division to avoid rounding an hourly rate down to a per-minute rate too early.

Figure 4. Invalid explicit values are rejected; they do not trigger a fallback to the default rate.

Changing the student's rate affects newly scheduled lessons only. Previously scheduled lessons, including future appointments, keep their saved fee. Editing a lesson's duration also keeps its fee; the tutor must use edit L1 f/AMOUNT to change the charge. This protects negotiated prices and prevents an administrative edit from changing payment history. Fee statements read Lesson.getFee() for the saved charge; income reads getAmountPaid(), while outstanding-balance summaries read getAmountOwed().

An explicit fee edit also preserves the amount received. Raising the fee of a paid lesson creates a remaining balance; reducing it exactly to the amount received settles the lesson. A fee below the amount already paid is rejected before any detail is replaced. Constructors and copy operations derive status consistently: a zero-fee lesson is already paid, with zero income.

Defensive checks and persistence

Rates accept non-negative decimal dollar amounts with at most two fractional digits. Durations accept whole minutes from 1 to 1440. Model validation throws IllegalArgumentException, so these rules apply to direct calls and hand-edited files even when assertions are disabled. The command layer catches these exceptions and returns Error: .... Assertions check programming invariants, such as preserving student identity and advancing counters only after successful insertion. Debug logging records rate changes, calculation results and rejected commands without adding messages to normal command output.

The data file keeps the legacy student layout because every trailing student field is already a subject. Inserting a rate into that layout could misread an existing subject as money. Instead, an optional R | S1 | 60 record stores a student's rate. New lesson lines end with NOTES | CANCELLATION_REASON | MINUTES | AMOUNT_PAID, using an empty cancellation reason for active lessons. Separate fields prevent a cancellation reason such as 90 from being confused with a 90-minute duration. Legacy ten-field rows and upstream eleven-field cancellation rows still load, with a default duration of 60. Files saved by the earlier hourly-rate branch used field eleven for duration; their generated NOTES | MINUTES header identifies that layout. Headerless eleven-field rows retain upstream's cancellation semantics. Loading preserves the saved total fee and never recalculates it from current rates.

Immutable lesson copies retain both cancellation and duration. Rescheduling keeps the chosen fee; cancelling retains its recorded amount for history while excluding it from amounts owed. An edit to a cancelled lesson cannot give it attendance, even if it also changes the duration.

Students load in the first pass. The second pass applies rates and imports linked records, allowing lines in any order. Invalid or orphaned rate lines are skipped with their line numbers; a duplicate rate line cannot override the first valid rate. A bad rate does not discard the student or their history. Encoding includes rate records and durations, so the existing snapshot comparison automatically saves changes. The new application reads old files; older application versions cannot read all new records, so keep a backup before using the new version if a downgrade may be necessary.

Alternatives, limits and verification

A separate rate command was considered. Extending add and edit uses familiar commands and supports entering a complete student in one line. Storing only the rate on lessons and calculating fees whenever displayed was also considered. Saving the chosen total instead keeps historical amounts stable. Per-subject rates, effective-date rate histories and automatic recalculation are possible future extensions; they would need explicit rules for existing and paid lessons.

Duration currently supports billing and display. Conflict checking retains the existing identical-start rule; it does not detect overlapping lesson intervals. Adding interval scheduling would be a separate enhancement requiring corresponding tests and documentation.

DefaultHourlyRateTest exercises command validation, decimal rounding, overrides, rate clearing, immutable copies, payment totals, legacy files, malformed records and save/restart behaviour. Fee statements

fee_statement STUDENT_ID is handled by PaymentCommands. It resolves the student, reads the shared lesson collection, and builds the statement when requested; no separate statement record is stored. The command includes every stored lesson for that student, whether paid, partially paid or unpaid and whether in the past or future. Rows are ordered by date, start time, then lesson ID, and display the saved fee and payment status alongside the lesson ID, date and subject. Partial-payment rows also show the amount received. A missing or extra argument and an unknown student produce an error; a valid student with no lessons gets an explicit empty-history message.

Figure 5. The statement is assembled from the selected student and their stored lessons; it does not introduce a new domain object.

The command validates that exactly one student ID was supplied before looking up the student. It then filters lessons by that student's ID and sorts them before formatting each row. This is deliberately different from unpaid and owed, which consider remaining balances on non-cancelled lessons dated today or earlier. Fees and payment statuses come from each Lesson, so the statement does not recalculate charges or change payment state.

Interaction with payment and lesson features

The statement reads each lesson's saved total fee and payment status. It does not consult the student's current hourly rate or recalculate a fee, so changing a rate affects future scheduling but cannot rewrite the amounts shown for existing lessons. Recording attendance and rescheduling preserve payments. Editing the fee preserves the amount received but may change the derived payment status: a larger charge can turn a paid lesson into a partially paid one; reducing the charge to the amount received settles it. An edit below the amount received is rejected. Free lessons are always settled and add no income.

mark LESSON_ID paid and mark LESSON_ID unpaid update payment status on a replacement Lesson in TutorLedgerData. The next fee statement displays that status. By contrast, unpaid and owed are outstanding-balance views: they include non-cancelled lessons dated today or earlier with a remaining balance, including partial payments, and report the amount still owed. fee_statement intentionally shows the full stored history, including paid, future and cancelled lessons. A cancellation therefore remains visible in the history, even though it is excluded from the amounts due.

Defensive checks and persistence

The command requires exactly one student ID: an empty value or any extra whitespace-separated argument returns the usage message. TutorLedgerData.getStudent validates the ID format, normalises it to the canonical uppercase key and reports an unknown student; the statement converts that exception to a user-facing error. Matching lessons are filtered against the resolved student ID without regard to case. getLessons() returns a copy of the collection, and the command sorts a stream into a new list, leaving the stored order unchanged. Sorting by date, time and lesson ID produces deterministic output even when lessons share a date or start time.

Lesson constructors validate fees as non-negative dollar amounts with at most two decimal places and store them as BigDecimal. The statement formats those already-validated values to two decimal places without converting through floating point. Dates use the English weekday formatter so display is consistent regardless of the machine's default locale.

The statement creates no data and writes no statement record. The main loop still takes its usual pre-command storage snapshot and calls saveIfChanged afterwards, but this read-only command leaves the snapshot unchanged, so no file write occurs. mark does change a lesson; the standard snapshot check then saves its updated payment status along with the lesson's existing fee. The storage format keeps these values on the lesson record, so the statement after restart reads the same fee and latest saved status.

Alternatives, limits and verification

Generating a statement from the live lesson collection avoids a second payment-history store that could drift out of sync with lesson edits, deletions or reloads. It also means the statement reflects the current stored lesson details rather than preserving a separate point-in-time document. The feature formats output for the terminal; exporting or printing a statement would be a separate capability.

PaymentCommandsTest checks that statements include only the selected student's lessons, include both paid and unpaid fees in date order, and report empty histories and invalid student arguments. The same suite checks payment-status updates that the statement reads, as well as the intentionally narrower date and cancellation filters used by unpaid and owed.

Appendix A: Product scope

Target user profile

Independent tutors teaching primary-school, secondary-school and junior-college students, who are comfortable entering commands in a terminal and need to manage their own tutoring records locally.

Value proposition

TutorLedger keeps student profiles, lesson schedules, homework, scores, payments and follow-up tasks together. Default rates reduce repeated entry, historical records support lesson preparation, and explicit deletion confirmation helps prevent accidental loss. The application records payments; it does not process money, deliver online lessons, or send messages to students and parents.

Appendix C: Non-functional requirements

  • Runtime: the application is built for Java 25 and is operated through a terminal.
  • Offline operation: the product's commands use local data and do not require a network service.
  • Persistence: records are kept in a human-editable local file and restored across restarts. The working directory must permit file writes; failed saves are reported to the user.
  • Monetary precision: money uses decimal arithmetic with explicit rounding for calculated charges.
  • Input errors: rejected commands report a useful message without applying a partial update.
